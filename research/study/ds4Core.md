# DwarfStar (ds4) Deep-Read Report — research/ds4

## 1. Overall architecture, model support matrix, forward pass, threading

**What it is.** A deliberately narrow, vertical C inference engine (antirez, "DwarfStar"), NOT a general GGUF runner (README.md:5-9, AGENT.md:3-4). One giant file `ds4.c` (64,541 lines) owns GGUF mmap loading, tokenizer, CPU reference kernels, Metal graph scheduling, sessions, and disk-cache serialization (ds4.c:1-15, AGENT.md:33-40). `ds4_metal.m` (1.79MB, Obj-C) owns only Metal objects: device/queue/library, mmap-backed no-copy weight views, command batching, kernel wrappers (ds4_metal.m:25-34). Kernels live in `metal/*.metal` (moe.metal, flash_attn.metal, dsv4_hc.metal, dsv4_kv.metal, dense.metal, etc.). Depends only on `-lm -pthread` + Foundation/Metal frameworks — **no GGML link, no Accelerate, no C++** (Makefile:17,26; AGENT.md:25 "Do not introduce C++"). Acknowledges llama.cpp for quant layouts/tables/dot logic (README.md:45-56).

**Model support matrix** — exactly three hardcoded shapes, selected by exhaustive GGUF-metadata match, `exit(1)` otherwise (ds4.c:535-653, 5324-5430):
- **DeepSeek V4 Flash** (284B total/13B active, 1M ctx): 43 layers, embd 4096, vocab 129280, 64 heads, MLA-like 1 KV head × 512 dim, q_lora 1024, 256 routed experts, 6 used, 1 shared, ff_exp 2048, SWA 128, indexer 64 heads×128 dim top-k 512, 4 hyper-connection streams w/ 20 Sinkhorn iters, expert_weight_scale 1.5.
- **DeepSeek V4 Pro** (1.6T/49B active): 61 layers, embd 7168, 128 heads, q_lora 1536, 384 experts/6 used, ff_exp 3072, indexer top-k 1024, scale 2.5.
- **GLM 5.2** (family GLM_DSA): 79 layers, embd 6144, vocab 154880, MLA (kv_lora 512, key/value_mla 256), 256 experts/8 used, 3 leading dense layers, nextn_predict 1 (in-GGUF MTP), indexer 32 heads top-k 2048, no HC, no SWA, rope base 8e6.

**Attention (DeepSeek)**: Compressed Sparse Attention + Heavily Compressed Attention (MODEL_CARD.md:25-66): per layer a raw 128-token sliding-window KV ring; layers 0-1 raw-only; even layers ≥2 ratio-4 compressed KV + a second indexer-KV stream with FP4-QAT'd Hadamard-rotated indexer scores selecting top-512 compressed rows; odd layers ≥3 ratio-128 compressed KV only (ds4.c:1065-1079 hardcodes the expected pattern; validated against `deepseek4.attention.compress_ratios` metadata at ds4.c:5432-5466). This is why 1M ctx ≈ only ~26GB KV (README.md:1116-1121). Indexer activations get an exact 128-wide Hadamard + FP4 (e2m1) activation-simulation round-trip to match the official graph (ds4.c:3288-3296).

**Forward pass (Metal, the production path)**: whole-model layer-major graph with one fixed DS4-specific tensor set for single-token decode and another for batched prefill — no generic graph arena, every buffer names a model stage (ds4.c:14829-14918). Decode: token embedding enters `cur_hc` (4 hyper-connection streams), per layer: HC pre-mix → attention (Q8_0 q_a/q_b LoRA projections, RoPE 64-dim, raw SWA ring + compressed attention with indexer top-k, output via grouped low-rank out-proj a/b) → HC post → MoE FFN (shared Q8_0 expert always; router `ffn_gate_inp`+bias picks 6, IQ2_XXS gate/up matvecs → SwiGLU (clamped) → Q2_K down, results folded by `kernel_dsv4_moe_sum6_f32`; an 8-way `sum8` variant exists for GLM) → HC combine; after 43 layers, output norm + Q8_0 output head → logits (ds4.c:14846-14849, metal/moe.metal:263-300). Prefill is chunked (default 4096 tokens; 2048 in CUDA-TP mode) reusing the same range-capable layer-major graph per chunk (README.md:837-843). Sessions: `ds4_session_sync()` takes full token prefixes and reuses/extends/rebuilds the live KV checkpoint (ds4.h:11-17, 354-363).

**Threading model**:
- CPU backend: one persistent pool, default `min(12, online CPUs)` (env `DS4_THREADS`), hard cap 32; row-parallel `ds4_parallel_for` with 512-row minimum, generation-counter condvar handoff, main thread takes the first slice (ds4.c:1766-1924).
- Metal: single encoding thread accumulating commands into a batch command buffer + pending-CB list (ds4_metal.m:53-56); plus a dedicated **async selected-expert load service thread** for streaming (ds4.c:20879-20990, registered at ds4_metal.m:448-456); plus a **pread worker pool, default 9 threads, cap 18** (`DS4_METAL_STREAMING_EXPERT_PREAD_THREADS`, ds4_metal.m:10802-10815, pool at 10884-11049); plus prefill page-in workers, default 8, cap 16 (ds4.c:18377-18391).
- Server: single live KV session by default; `--batched-session N` preallocates N resident KV sessions with exact micro-batched decode (native shared-expert/QKV batching on Metal Flash from 2 rows up, ordered exact fallback otherwise) (README.md:978-1001).
- Process-level: an intentional instance lock prevents two huge model processes (ds4.c:737, AGENT.md:29-30).

## 2. SSD streaming (the part most relevant to Kimi K3 on 64GB)

**Caution**: `ds4_ssd.c` (210 lines) is only budget planning + a `--simulate-used-memory` mlock tool (ds4_ssd.c:108-135,137-202). The real streaming engine is inside ds4_metal.m + ds4.c.

**What stays resident vs streams**: all non-routed weights (attention, dense FFN, shared experts, router, embeddings, output head) are resident, wrapped as no-copy MTLBuffers over the mmap and pinned via MTLResidencySet (ds4_metal.m:236,1601-1610; up to 4096 model views, ds4_metal.m:525-538). Only routed-expert tensors stream. Auto budget: 80% of Metal's `recommendedMaxWorkingSetSize` (env `DS4_SSD_AUTO_CACHE_PCT` 50-95; comment explains 80% is the measured OOM-safe point on unified memory, ds4_ssd.c:95-105) minus non-routed bytes → expert count; then **headroom for two full routed layers is reserved for overlapped streaming prefill** (ds4.c:53555-53572: "two routed prefill layers need X GiB"); GLM Metal additionally caps the graph at a 12GiB VM-pressure guard (ds4.c:53300-53315).

**RAM expert cache**: direct-indexed 2-D table `g_stream_expert_cache[80][384]` (layer × expert), each entry = three MTLBuffers (gate/up/down) + absolute GGUF offsets + last_used + use_count (ds4_metal.m:541-598). Backing memory is a **single-size-class slab allocator**: up to 256 slabs, per-expert slot = 2×gate_bytes+down_bytes frozen at first sight; off-size layers (mixed-precision Q4 boost layers among IQ2) are *rejected* to the mapped-model path rather than adopted, to avoid poisoning the slab class (ds4_metal.m:10495-10508, 11380-11417). Global residency policy — any layer may use any slot; no per-layer cap (ds4_metal.m:10530-10541).

**Eviction**: route-hotness LFU with LRU tiebreak. Hotness counts every *selection* (even misses), incremented per routed token, halved every 16 decode tokens (`DS4_METAL_STREAM_EXPERT_HOTNESS_DECAY_TOKENS`, ds4_metal.m:549, 11515-11624). Victim scan is a full 80×384 sweep picking lowest hotness then oldest last_used, skipping in-flight and protected (currently-selected) entries; batch variant collects up to 8 victims at once and recycles their MTLBuffers directly as reusable buffers (zero realloc) (ds4_metal.m:12542-12879). Comment at 12554-12558 explains why hit-count LFU was rejected (penalizes experts evicted before a second hit).

**I/O syscalls (macOS-specific)**:
- Model opened once; fd kept (`g_model_fd`); base access is mmap (loader parses only header/metadata/tensor directory; data stays in page cache, ds4.c:11-15).
- Cache-miss expert loads: plain **`pread()`** loops (EINTR-safe, chunked ≤SSIZE_MAX) into the slab MTLBuffer contents (ds4_metal.m:10824-10868). Three tasks per expert (gate, up, down offsets) — up to 8 experts × 3 = 24 tasks fanned across the pread pool (ds4_metal.m:10735-10751).
- Prefetch: **`fcntl(F_RDADVISE)`** (macOS readahead advisory) over expert byte ranges, chunked ≤INT_MAX (ds4_metal.m:10684-10716); prefill page-in alternatively uses `posix_madvise(WILLNEED)` or touch-read paths, selectable per job (ds4.c:18291-18328).
- Eviction hygiene: optional **`posix_madvise(POSIX_MADV_DONTNEED)`** on the evicted expert's mmap range (page-aligned), opt-in via env (ds4_metal.m:11429-11486).
- **No F_NOCACHE / O_DIRECT anywhere** — the design deliberately rides the unified page cache; the disk-KV code even avoids mmap for cache files "so restoring cache entries does not add more VM mappings" (README.md:1306-1308).

**Latency hiding (decode)**: per layer the router's selected-expert set is split into resident-mask/missing-mask; resident experts' matvecs are submitted immediately while the service thread preads missing ones; results bound in a second stage. The split path is only taken when ≥3 experts miss (extra command stage + second bind cost, ds4_metal.m:10561-10572) and only after warmup (≥4 decode tokens and ≥1024 cached experts or half budget, ds4_metal.m:11492-11513). AGENT.md:11 states the principle: hide missing-expert loads behind shared-expert + resident-expert inference.

**Latency hiding (prefill)**: layer-major streaming prefill loads the *next* layer's full routed expert set (multi-threaded page-in, prepare-ahead depth 1-4, `DS4_STREAM_PREFILL_MAX_PREPARE_AHEAD`, ds4.c:18433-18447) while the current layer computes; the expert-cache budget reserves two full routed layers as double-buffer headroom. GLM variant keeps the largest full-layer *prefix* resident (auto: budget/7 capped at 10GiB, ds4.c:53490-53513) and streams the rest.

**Hot-expert seeding**: ships compiled-in hotlists (`ds4_streaming_hotlist.inc` — {layer, expert} pairs sorted by profiled hits for Flash/Pro; `_glm52.inc` for GLM) used to preload the cache at startup up to the budget; a profiler can record per-run selected-ID counts and merge them into a file for regeneration (ds4_metal.m:1230-1400, ds4.c:20408-20475, 29599-29704). `--ssd-streaming-cold` disables preload for measurement.

**Per-layer stats**: hits/misses/evictions/pread GiB/ms per layer, hit-rate reporting, plus a ~40-field timing summary (read/sync/copy/bind/slot/prune/addr/wait/prepare/reuse-scan/readahead) behind env flags (ds4_metal.m:3115-3480).

## 3. "Layer pack" (ds4_layer_pack.c/.h) — NOT an on-disk format

Despite the name, this is a **multi-tier layer placement packer** for multi-GPU/CPU splits: given per-entry byte sizes in forward order (entry 0 = embedding pseudo-layer, 1..n = transformer layers, n+1 = output head) and per-GPU byte budgets, it produces a monotonic-contiguous assignment — walk entries, advance device when budget exceeded, spill remainder to CPU tier; no backtracking (ds4_layer_pack.c:14-45, header contract ds4_layer_pack.h:22-48). Pure C99, shared by CUDA and Metal builds, max 16 GPUs. Designed this way because monotonic contiguity preserves the pipeline order and makes placement predictable/printable (`ds4_layer_pack_print` emits the "GPU0: layers 0-21 + embedding (38.4/40.0 GB)" layout). On-disk formats in this repo are instead: GGUF (model), KVC/DSV4 (KV cache, §5), and split GGUFs per layer range for distributed PRO Q4 (README.md:439-443).

## 4. Quantization

**Asymmetric routed-only 2-bit scheme** (README.md:97-100): only routed MoE experts are quantized hard — gate/up at **IQ2_XXS**, down at **Q2_K** (down gets the better format because it accumulates); shared experts, all attention projections, router, embeddings, output stay **Q8_0/F16/F32**. Routed experts dominate model bytes, so total ≈ 81GB for Flash 2-bit. Variants: `q2-q4-imatrix` upcasts last 6 layers' experts to Q4_K ("boosted" layers, handled by the mapped-model fallback path since they break the slab size class, ds4.c:4533-4534); `q4-imatrix` all-Q4_K experts; GLM routed gate/up Q2_K/Q4_K/Q5_K, down up to Q6_K (README.md:148-152). All prefer **imatrix** builds (routed-MoE imatrix collected with in-repo tooling under gguf-tools/imatrix). Supported tensor types total: F16, F32, Q8_0, Q2_K, Q4_K, Q5_K, Q6_K, IQ2_XXS + Q8_K activation blocks (ds4.c:2044-2050, 745-756).

**Quality methodology**: not perplexity but avg_nll of official DeepSeek-API continuations, token-by-token, 100-case fixture (`gguf-tools/quality-testing/score_official`, CONTRIBUTING.md:79-105); plus logprob-vector regression against official API top-logprobs (README.md:1527-1543); plus the 92-question ds4-eval capability suite. Claimed: the 2-bit quants "behave well, work under coding agents, call tools in a reliable way" (README.md:94-95).

**Dequant/dot implementation**: activations quantized to Q8_K (256-elem blocks) once and reused across all selected expert rows (ds4.c:3304-3306); NEON `vdotq_s32` integer dot kernels for IQ2_XXS (grid-table expansion + sign tables), Q2_K, Q4_K, Q8_0 with dotprod-guarded fallbacks (ds4.c:3349-4030); fused gate/up pair matvec with SwiGLU. Metal mirrors these as `kernel_mul_mv_id_iq2_xxs_sum6_f32`, `_q2_K_sum6`, `_q4_K_sum6` plus slots6/addr/table/masked variants for the streaming address-table paths (metal/moe.metal:5477-6446). CUDA reuses IQ2 tables via `ds4_iq2_tables_cuda.inc`.

## 5. KV store (ds4_kvstore + rax) — persistent KV cache & session resume

**Purpose**: chat APIs are stateless; the server keeps ONE live in-memory KV checkpoint (RAM reasons) and uses the disk cache as the cross-session/restart resume mechanism (README.md:1288-1292).

**File format** (`<sha1>.kv`, key = SHA1 of *rendered byte prefix*, not tokens — survives retokenization differences): 48-byte KVC header (magic "KVC", version, routed quant bits, save reason cold/continued/evict/shutdown, extension flags, token count, hit count, ctx size, model_id byte, created/last-used times, payload bytes) + u32 text length + rendered UTF-8 text + DSV4 session payload + optional trailers (README.md:1316-1378; ds4_kvstore.h:11-57; header ABI byte notes ds4_kvstore.c:25-41). DSV4 payload v2: 13 LE u32 fields (ctx size, prefill chunk, raw ring cap, SWA len, comp cap, token count, layer count, KV dim, indexer dim, vocab, live raw rows) then checkpoint token IDs, **full float32 logits for the next token** (resume without re-decode), per-layer compressed/indexer row counts, raw SWA rows in logical order, compressed rows + compressor frontier tensors, indexer rows + frontiers (README.md:1380-1416; magic/versions ds4.h:446-451). Written with plain read/write, deliberately not mmap (README.md:1306-1308).

**Policy**: store ≥512 tokens; cold saves ≤30k tokens, trim 32 tail tokens and align down to 2048-token chunk boundary (BPE-boundary defense + matches prefill chunk schedule so compressor row finalization is identical to a cold prefill, ds4_kvstore.c:33-42); continued saves every ~10k tokens at absolute frontiers; evict/shutdown saves. Eviction scoring: hits decayed with 6-hour half-life, minimum effective hits 0.01, continued-prefix waypoints heavily discounted (0.05/0.45 factors), cold/evict/shutdown anchors get 2.0 prior (ds4_kvstore.h:13, ds4_kvstore.c:43-56). Cross-quant reuse allowed by default (2-bit ↔ 4-bit) since KV state comes from Q8 attention either way.

**rax (Redis radix tree) usage**: NOT for KV files — it backs the server's **exact-DSML tool-replay maps**: `by_id` (unguessable API tool-call ID → exact sampled DSML block) and `by_block` (dedupe), bounded at 100k IDs (ds4_server.c:8199-8495). Guarantees the next-turn rendered prompt is byte-identical to what the model sampled so the live KV checkpoint stays valid; canonical JSON→DSML re-rendering is only the fallback, which may force checkpoint rewrite or disk-snapshot restore + suffix replay (README.md:1060-1090). The map is persisted as a KVC trailer section ("KTM") so replay survives restarts.

**Agent**: sessions in `~/.ds4/kvcache`; `/save /list /switch /del /strip`; full-KV sessions resume with **zero prefill** (README.md:791-799).

## 6. Speculative decoding (DSpark)

DSpark is DeepSeek's released draft model for Flash, packaged as a 5.6GiB support GGUF (README.md:187-229). Integration: the main Metal graph captures hidden states at up to 8 metadata-specified target layers (`deepseek4.dspark.target_layer_ids`, capture mask machinery ds4.c:25617-25710); DSpark stages (≤8) each have main_proj/main_norm, a full transformer block, a rank-reduced Markov head (markov_w1/w2), and a confidence projection (ds4.c:4118-4147); block_size (5) tokens are proposed per cycle, embedded via `dspark_draft_tokens`/`dspark_draft_hc` and verified by one batched target pass; only the accepted prefix commits — graph state mutation is guarded by saved compressor frontiers (spec_* tensors + prefix1 cheap partial-accept state for N=2, ds4.c:14887-14904). Confidence threshold default 0.9 prunes unlikely suffixes; greedy-only (sampled decoding ignores DSpark); `--quality`/`--dspark-strict` force target-only. Status: experimental, "at most a slight speedup" (README.md:135-137). GLM instead has an in-GGUF one-step MTP block (`--glm-mtp`). MTP is disabled under session batching. Draft state is not persisted in KV files; rebuilt after load (README.md:1414-1416).

## 7. CPU compute

CPU backend is explicitly **reference/debug only** (AGENT.md:12, README.md:1511-1514); production is Metal/CUDA/ROCm. Kernels: NEON with `__ARM_FEATURE_DOTPROD` `vdotq_s32` paths for all quant dots, scalar fallbacks; f16↔f32 via NEON vcvt (ds4.c:3090-3128). GEMM strategy: there is no blocked GEMM — everything is row-parallel matvec over the thread pool (per-token decode shape), with Q8_0/Q8_K activation pre-quantization amortized across expert rows and a fused gate+up pair kernel (ds4.c:10443-10470). **No Accelerate/BLAS on macOS CPU path** (Makefile links only -lm -pthread + Metal/Foundation). Build flags: `-O3 -ffast-math -mcpu=native` (Makefile:5-14). A macOS kernel VM bug makes large CPU runs dangerous on Macs (CONTRIBUTING.md:75-77, AGENT.md:28-29).

## 8. Model-specificity — what porting to Kimi K3 would require

The engine is philosophically model-specific; every layer of it asserts DeepSeek/GLM shapes. Complete list of arch-specific assumptions found:

1. **Fixed shape tables** (ds4.c:535-653) + exhaustive 22-field metadata match with `exit(1)` on mismatch (ds4.c:5324-5430, config_expect_* 5496-5640). Kimi K3 needs a fourth `ds4_shape`, a `kimi3.*` (or whatever) GGUF metadata namespace parser (cf. `deepseek4.*` keys ds4.c:5532-5557, `glm-dsa.*` 5647+), and a new `ds4_variant`.
2. **Attention machinery is the deep problem**: raw-SWA-ring + ratio-4/128 compressed KV + indexer top-k is baked into (a) the expected-ratio function ds4.c:1065-1079, (b) the Metal graph's persistent per-layer cache tensors (raw ring, attn_comp cache, attn/index compressor frontier state, ds4.c:14872-14903), (c) the DSV4 session payload format (13-field header + per-layer comp/indexer rows, ds4.h:446-451), (d) flash_attn.metal / dsv4_kv.metal kernels, (e) context-memory estimators. **Kimi Delta Attention** (a linear/delta-rule state, per Kimi K2 lineage) would replace nearly all of this with a per-layer fixed-size recurrent state — simpler KV (great for RAM) but a new cache/serialization/graph design, not a parameter tweak. Nothing in ds4 supports recurrent-state layers.
3. **Hyper-connections**: DeepSeek keeps 4 HC streams per token with Sinkhorn mixing; hc_pre/hc_post/hc_comb views thread the whole graph (ds4.c:9580-9588, 14846-14856) and even MTP/DSpark heads carry hc_head_* tensors. GLM path shows HC can be zeroed out (n_hc=0), so **Kimi "attention residuals"** would likely follow the GLM-style plain-residual path, but any nonstandard residual (e.g., residual on attention outputs across layers) needs new graph plumbing + kernels (dsv4_hc.metal).
4. **MoE config hard caps**: `DS4_METAL_MAX_ROUTED_EXPERT_USED = 8` (ds4_metal.m:494) — router top-k >8 breaks the streaming cache load path arrays; streaming cache dimensions `MAX_LAYER=80`, `MAX_EXPERT=384`, `MAX_ENTRIES=80×384` (ds4_metal.m:541-548); `DS4_MAX_LAYER=79` (ds4.c:456). Kimi K3 at 2.8T likely has ≥61 layers (fits) but very possibly >384 experts and/or >8 active → all these constants and the {u16,u16} hotlist format must grow. Metal `sum6`/`sum8` reduction kernels bake the used-expert count (metal/moe.metal:263-300) — need sumN.
5. **Router details validated**: `expert_weights_norm` must be true, `expert_group_count`/`expert_group_used_count` must be 0 (ds4.c:5597-5640) — if K3 uses grouped/limited-device routing (DeepSeek-V3 style) or sigmoid-vs-softmax differences, the router kernel and validation change.
6. **Per-tensor quant-layout expectations**: every non-routed tensor's type/shape is asserted (e.g., attn q_a/q_b/kv Q8_0 at ds4.c:5039-5062); grouped low-rank attention output (n_out_group 8/16 with output_a/output_b LoRA) is DeepSeek-specific; only specific routed-quant combos have kernels (ds4.c:6081-6130).
7. **Tokenizer/template/tool protocol**: DeepSeek BPE + DSML tool-call format is woven through server, agent, exact-replay rax maps, streaming greedy-syntax sampling (README.md:1060-1090); Kimi uses different special tokens and (likely) different tool markup → new renderer + parser + agent prompt.
8. **Speculative decoding**: DSpark/MTP weights layouts are DeepSeek's (ds4.c:4106-4147); K3's MTP head (if any) needs its own binder.
9. **KV file compat**: model_id byte reserves 0=Flash; new shapes need nonzero ids (ds4.h:246-248, ds4_kvstore.h:44-46).
10. **What ports cleanly** (arch-agnostic gold): the entire SSD streaming subsystem design (slab cache, hotness LFU, pread pool, F_RDADVISE, split resident/missing dispatch, prefill double-buffer), the KVC/kvstore machinery, thread pool, quant dot kernels, layer_pack, and the session_sync prefix-reuse discipline. antirez's own precedent: GLM 5.2 (a different family: MLA, no HC, no SWA, dense leading layers, in-GGUF MTP) was added as a second family with its own graph path — that is the realistic template and effort scale for a Kimi K3 port.

## 9. Stated performance numbers

Metal CLI, ctx 32768, greedy, -n 256 (README.md:242-255): M3 Max 128GB q2: 58.5 t/s prefill short / 250.1 long, gen 26.7→21.5 t/s. **M5 Max 128GB q2: 87.3/463.4 prefill, 34.3/25.9 gen**. M3 Ultra 512GB q2: 84.4/468.0, 36.9/27.4; q4: 79.0/448.8, 35.5/26.6; **PRO q2 @32k: 138.8 prefill, 9.6 gen**. DGX Spark GB10 q2: 343.8 prefill, 13.8 gen. CSVs (speed-bench/): M4 Max q2 @2k: 343.8 prefill/26.8 gen; M2 Ultra: 410.6/23.2; GB10: 402.9/14.2; PRO-on-M3-Ultra: 183.1/12.4 declining to ~147/9.8 @14k. SSD streaming: GLM 5.2 IQ2_XXS (188GiB) on ONE M5 Max 128GB = **~4.8 t/s decode, 3-5 t/s prefill**; same model TP over two M5 Max via TB5/RDMA = ~16.8 t/s decode, ~94 t/s prefill @4096 (README.md:663-667). PRO q2 streaming on M5 Max 128GB: auto budget picked ~59GB expert cache (README.md:331-336). Distributed pipeline (2× M5 Max TB5, Q4 Flash): prefill 582-674 t/s (1.38-1.85× vs single), decode 24.7 vs 30.6 single (-19.4%) (README.md:407-421). 8×L40S server: 120 t/s aggregate gen, 2000 t/s prefill (README.md:30). PRO Q4 across two 512GB M3 Ultras: 11.5 t/s gen (README.md:454-456). 64GB Macs explicitly supported: q2 Flash + `--ssd-streaming --ssd-streaming-cache-experts 32GB` (README.md:305-316). Claude Code/opencode/Codex work against ds4-server; ~25k-token initial prompts amortized by disk KV (README.md:1263-1266).

## 10. Design philosophy & deliberate exclusions

Philosophy (AGENT.md:8-30, README.md:5-25): specialize for a few frontier open models on real consumer machines (128GB laptops, 512GB workstations); production path = whole-model Metal graph; mmap for resident, explicit reads for streaming, always hide I/O behind compute; correctness before speed — no unexplained logits drift tolerated, official-API vectors as ground truth; small/sharp/readable C "in a state of grace", comments beside code not design docs; narrow public API (CLI/server never see tensor internals); model support is opportunistic — models get **removed** when superseded. Explicitly excluded: generality (not a GGUF runner — arbitrary GGUFs rejected), C++, GGML dependency, permanent semantic flag-variants (diagnostic switches only), CPU as a production path, mmap for KV cache files, encryption/auth on the distributed protocol (trusted networks only), Accelerate/BLAS. AI-assisted development openly disclosed (README.md:41-43). Testing culture: correctness + speed regression tracks both mandatory for PRs (CONTRIBUTING.md:3-10), deterministic 4-question token-count gate, release QA matrix across Metal/CUDA/ROCm.

## KEY FACTS
- ds4 supports exactly 3 hardcoded model shapes (DeepSeek V4 Flash 43L/4096d/256exp/6used, Pro 61L/7168d/384exp/6used, GLM 5.2 79L/6144d/256exp/8used) matched field-by-field against GGUF metadata with exit(1) on any mismatch (ds4.c:535-653, 5324-5430)
- SSD streaming keeps ALL non-routed weights resident (no-copy MTLBuffers over mmap, pinned via MTLResidencySet) and streams only routed experts; auto budget = 80% of Metal recommendedMaxWorkingSetSize minus non-routed bytes, minus a reserved headroom of two full routed layers for overlapped prefill (ds4_ssd.c:95-135, ds4.c:53555-53572)
- Streaming expert cache is a direct-indexed [80 layers][384 experts] table of gate/up/down MTLBuffer triplets backed by a single-size-class slab allocator (max 256 slabs); eviction is route-hotness LFU (hotness counts selections including misses, halved every 16 decode tokens) with LRU tiebreak (ds4_metal.m:541-628, 11515-11624, 12542-12879)
- Cache-miss expert I/O = plain pread() into MTLBuffer contents via a worker pool of 9 threads default / 18 max; prefetch = fcntl(F_RDADVISE); eviction hygiene = optional posix_madvise(DONTNEED); NO F_NOCACHE or O_DIRECT anywhere (ds4_metal.m:10684-10716, 10802-10868, 11429-11486)
- Decode split path: resident experts dispatch immediately while a dedicated service thread preads missing experts; split only taken when >=3 of the selected experts miss (ds4_metal.m:10561-10572); prefill hides I/O by page-in of the NEXT layer's full expert set (8 threads, prepare-ahead 1-4 layers) during current-layer compute (ds4.c:18377-18447)
- 2-bit quant recipe: ONLY routed experts quantized - gate/up IQ2_XXS, down Q2_K, imatrix-tuned; shared experts/attention/router/output stay Q8_0; Flash 2-bit = 81GB total; quality gated by avg_nll vs official DeepSeek API continuations, not perplexity (README.md:97-100, CONTRIBUTING.md:79-105)
- Disk KV cache: file = 48-byte KVC header + rendered prompt text + DSV4 payload (exact tokens + full fp32 next-token logits + per-layer raw SWA rows/compressed rows/compressor frontier tensors); filename = SHA1 of rendered byte prefix; cold saves trim 32 tokens and align to 2048-token prefill-chunk boundaries; full sessions resume with zero prefill (README.md:1316-1445)
- rax radix trees back the exact-DSML tool-call replay map (unguessable tool ID -> exact sampled bytes, 100k entries) so re-rendered prompts stay byte-identical to the live KV checkpoint; canonicalization is only a fallback (ds4_server.c:8199-8495, README.md:1060-1090)
- ds4_layer_pack is NOT an on-disk format: it is a monotonic-contiguous greedy layer-placement packer for multi-GPU/CPU-spill (embedding + N layers + output head vs per-device byte budgets) (ds4_layer_pack.c:14-45)
- Hard caps that block Kimi K3 as-is: DS4_MAX_LAYER=79, streaming cache 80 layers x 384 experts, DS4_METAL_MAX_ROUTED_EXPERT_USED=8, Metal MoE reduction kernels hardcode sum6/sum8 for 6/8 active experts, expert_group_count must be 0, expert_weights_norm must be true (ds4.c:456, ds4_metal.m:494/541-548, metal/moe.metal:263-300, ds4.c:5597-5640)
- DeepSeek attention = 128-token raw SWA ring + alternating ratio-4 (with FP4-QAT Hadamard indexer, top-512) / ratio-128 compressed KV; 1M context costs only ~26GB KV; this entire cache layout is baked into the Metal graph tensors and the DSV4 serialization (MODEL_CARD.md:25-66, ds4.c:1065-1079, 14872-14903)
- Measured: M5 Max 128GB Flash q2 = 87 t/s prefill short / 463 t/s @11.7k, 34.3/25.9 t/s gen; SSD-streaming GLM 5.2 (188GiB) on one M5 Max = ~4.8 t/s decode and 3-5 t/s prefill; PRO q2 streaming auto-picked ~59GB expert cache on 128GB; 64GB Macs are an explicitly supported config with q2 Flash + 32GB expert cache (README.md:242-255, 305-336, 663-667)
- CPU path: NEON vdotq dotprod kernels, Q8_K activation pre-quantization shared across expert rows, row-parallel matvec thread pool (default min(12,ncpu), cap 32, 512-row min grain); no Accelerate/BLAS; CPU is reference/debug only and can crash macOS kernel with huge mappings (ds4.c:1766-1924, 3304-3306, CONTRIBUTING.md:75-77)
- Engine has no generic graph IR: one fixed set of named per-stage Metal tensors for decode and another for prefill; prefill chunk default 4096 tokens; interactive sessions/server/agent all reuse one live KV checkpoint via full-token-prefix sync (ds4.c:14829-14918, ds4.h:354-363)
- DSpark speculative decoding: separate 5.6GiB support GGUF, reads hidden states from metadata-listed target layers of the main model, proposes 5-token blocks via per-stage transformer block + Markov head + confidence proj (threshold 0.9), greedy-only, currently only a slight speedup (README.md:187-229, ds4.c:4118-4147)
- Philosophy: vertical specialization for a few models, correctness gated on official API vectors, mmap-resident + explicit-read streaming with I/O always hidden behind compute, no C++, no GGML link, models removed when superseded (AGENT.md, README.md:5-25)

## IMPROVEMENT IDEAS
- Steal the whole streaming stack shape but relayout the GGUF for streaming: ds4 issues 3 separate preads per missing expert (gate/up/down at distant offsets, ds4_metal.m:10735-10751). For Kimi K3 pack each expert's gate+up+down contiguously (and consider grouping co-activated experts of adjacent layers) so a miss is ONE sequential read - on M1 Max NVMe this roughly triples effective IOPS per expert and lets F_RDADVISE readahead actually help
- Exploit Kimi Delta Attention's tiny recurrent state: KV memory goes from ~26GB/1M-ctx (DeepSeek compressed KV) to megabytes of per-layer delta state, so on 64GB nearly the entire (80% x 64GB - non-routed weights) budget can go to the routed-expert cache; also makes KVC-style session files tiny and instant to save/load - keep ds4's full-logits-in-snapshot trick
- Predictive expert prefetch instead of ds4's purely reactive cache: router logits for layer L+1 are computable as soon as layer L's hidden state exists; issue the pread pool work for predicted-missing experts one layer ahead of the graph (ds4 only does this for full layers during prefill, never during decode). Combine with cross-layer expert co-activation tables (extend ds4's hotlist profiler, ds4_metal.m:1230-1400) trained offline for K3
- Copy the two proven overlap tricks exactly: (a) decode-time resident/missing split with >=3-miss threshold and async service thread (ds4_metal.m:10561-10572, ds4.c:20879+), (b) prefill next-layer full-expert page-in double buffer with 2-layer budget reserve (ds4.c:53555-53572) - these are the measured levers that make streaming decode tolerable
- Raise/parameterize ds4's hard caps before anything else if forking it: DS4_MAX_LAYER=79, cache[80][384], MAX_ROUTED_EXPERT_USED=8, sum6/sum8 kernels, u16 hotlist entries - Kimi K3 (2.8T) almost certainly exceeds 384 experts and may route >8; generate sumN Metal kernels from the shape instead of hardcoding
- Adopt the asymmetric routed-only quant recipe with imatrix (IQ2_XXS gate/up + Q2_K down, everything else Q8_0) as the starting point for K3-on-64GB, and validate with ds4's avg_nll-vs-official-continuations method rather than perplexity; consider IQ1_S/IQ2_XS tiers for the coldest experts (quality-tiered quantization by hotlist rank) to shrink the streamed bytes per miss
- On M1 Max specifically: pread pool default of 9 threads matches the 10-core M1 Max almost perfectly, but test 6-8 (2 E-cores are weak and the encoder + service threads need cores); wire iogpu.wired_limit_mb guidance into startup like ds4's TP docs do (README.md:611-617) to let Metal wire >75% of 64GB
- Skip DeepSeek-style compressed-attention complexity entirely in a K3 engine: KDA + a handful of full-attention layers means the flash_attn/dsv4_kv/compressor/indexer kernel families (easily half of ds4_metal.m's complexity) are unnecessary; budget that engineering into the expert-streaming path, which is the actual bottleneck at 2.8T params
- Consider on-disk expert compression beyond quantization: at ~2-bit the expert blobs are high-entropy but an lz4/zstd-light frame around IQ2 blocks still saves 5-15%; on a ~5-7GB/s NVMe with 10 CPU cores idle during decode, trading CPU decompress for SSD bytes can raise effective expert fetch bandwidth - ds4 never does this
- Persist and pre-seed the expert cache across runs: ds4 ships compiled-in hotlists and can merge profiled runs; go further for K3 - dump the live cache's layer/expert set at shutdown and bulk-load it (sequential, sorted by file offset) at startup so the first prompt doesn't pay thousands of cold misses
- Keep ds4's session discipline verbatim: full-token-prefix session_sync, SHA1-of-rendered-bytes disk cache keyed with boundary trim/align, exact tool-call byte replay via radix tree - these are what make a local agent usable regardless of architecture, and they are architecture-independent code you can port almost unchanged
- Use ds4's eviction insight directly: selection-based hotness (count routed selections even on miss, decay by halving every N tokens) beat hit-count LFU in their testing (ds4_metal.m:12554-12558); for K3's larger expert count, replace the full 80x384 victim scan with a small heap or per-layer clock to avoid O(layers x experts) scans per miss batch
